# ChopNow Database Schema

PostgreSQL 17 · Prisma 7 · Source of truth: [`database/prisma/schema.prisma`](../database/prisma/schema.prisma)
plus the hand-written integrity migration
[`20261014161500_integrity_constraints`](../database/prisma/migrations/20261014161500_integrity_constraints/migration.sql).

## 1. Conventions

| Topic | Rule |
|---|---|
| Primary keys | UUIDv7 (time-ordered), generated by Prisma. |
| Names | Tables `snake_case` (`@@map`); columns `camelCase`. Quote columns in raw SQL: `SELECT "totalKobo" FROM orders`. |
| Money | `integer` kobo (NGN minor units). Never floating point. Per-row ceiling ₦21,474,836.47 (int4). Widen to `bigint` before any single settlement or payout could exceed ₦20m. |
| Percentages | Integer basis points (`1500` = 15%). |
| Timestamps | `timestamp(3)` in UTC. Restaurant opening hours are minutes after midnight in Africa/Lagos. |
| Coordinates | `double precision`, only where operationally needed (restaurants, addresses, rider last position). |
| Encoding | Databases **must** be created as UTF-8. Migrations are kept ASCII-only regardless. |
| Soft delete | Menu items, variants, extras and addresses have `deletedAt`. Orders keep snapshots, so history survives menu changes. |
| Enums | Mirrored in `packages/shared-schemas/src/enums.ts`; `services/api/test/schema-sync.test.ts` fails if they drift. |

## 2. Tables by module

**Identity & access**
- `users`: one row per person and a single `role`. Lower-cased unique email, optional unique E.164 phone, scrypt `passwordHash`, `status`, `tokenVersion` (bump to invalidate access tokens), lockout counters.
- `auth_sessions`: one row per refresh token, storing only its SHA-256 hash. `familyId` groups rotations; `replacedById` links each token to the one that replaced it.
- `customer_profiles`, `addresses`.

**Restaurants & menus**
- `restaurants`: owner, profile, location, `verificationStatus`, `isAcceptingOrders`, prep time, minimum order, delivery radius, optional commission override and denormalised rating.
- `restaurant_hours`: zero or more opening windows per weekday.
- `verification_documents`: shared by restaurants and riders (exactly one owner). Stores only a private-bucket `storageKey`.
- `menu_categories`, `menu_items`, `menu_item_variants` (full price per variant), `menu_item_extras` (price and max quantity).
- `favourite_restaurants`.

**Orders**
- `orders`: fulfilment `status` and `paymentStatus` are **separate** columns. Every amount, plus the commission rate and rider earning, is snapshotted at creation. Also holds the address snapshot (JSON), the 4-digit `deliveryPin`, the client `idempotencyKey` (unique per customer), `visibleToVendorAt` (set only once an online payment is verified) and lifecycle timestamps.
- `order_items`, `order_item_extras`: name and price snapshots.
- `order_status_history`: from, to, actor, role, reason and time. **Append-only.**

**Payments**
- `payments`: one row per online payment attempt (`INITIALIZED/SUCCESSFUL/FAILED/ABANDONED`) with our unique `reference`.
- `payment_events`: every webhook or verification result, unique on `(provider, dedupeKey)`, so a repeated webhook is stored once and processed once.
- `refunds`: their own records and status, each with an `idempotencyKey`; `chargeTo` (CUSTOMER_FUNDS, RESTAURANT, PLATFORM, UNAPPLIED_PAYMENT) and `method` (PROVIDER, MANUAL) are fixed at approval; for manual refunds `providerRefundId` holds the bank transfer reference.

**Riders & delivery**
- `riders`: type (CORE/INDEPENDENT), verification, availability, vehicle, zone, optional last position, stats, cash-limit override.
- `deliveries`: one per order. Holds `currentRiderId`, status, timestamps for each step, cash to collect, PIN attempts and the audited proof override.
- `delivery_offers`: one row per offer to a rider, with tier, expiry and response.
- `delivery_events`: the delivery timeline.

**Cash on delivery**
- `cash_collections`: per order, the amount due, collected and reconciled; collection, reconciliation and dispute status; and the responsible rider.
- `cash_remittances`, `cash_remittance_allocations`: cash a rider hands in, allocated to specific collections. Only `CONFIRMED` remittances reduce what a rider owes.

**Finance**
- `financial_transactions`: journal header with a unique `idempotencyKey` and links to the order, payment, refund, remittance or payout.
- `ledger_entries`: debit/credit lines per `LedgerAccount`, with a restaurant or rider sub-ledger.
- `rider_earnings`, `vendor_settlements`, `rider_settlements`, `payouts`: settlement lifecycle `DRAFT → APPROVED → PAYOUT_INITIATED → PAID/FAILED`. Payouts are recorded, never sent automatically.

**Engagement & support:** `reviews` (one per order), `promotions`, `promotion_redemptions`, `support_tickets`, `support_messages` (`isInternal` notes are never shown to customers).

**Notifications:** `notifications` (in-app history with a unique `dedupeKey`), `push_tokens`.

**Platform:** `platform_settings` (business rules JSON, validated by `BusinessRulesSchema`), `audit_logs` (**append-only**), `idempotency_keys`, `background_jobs` (Postgres-backed job queue).

## 3. Constraints

### Rules enforced by the database itself

| Rule | Mechanism |
|---|---|
| Email stored lower-case; phone is E.164 | `users_email_lowercase_chk`, `users_phone_e164_chk` |
| Unapproved restaurant cannot accept orders | `restaurants_accepting_requires_approval_chk` |
| Unapproved rider cannot be online (so gets no offers) | `riders_online_requires_approval_chk` |
| Prices and amounts never negative | `*_price_chk`, `orders_amounts_nonneg_chk`, … |
| `total = subtotal + delivery + service − discount` | `orders_total_formula_chk` |
| Delivery PIN is exactly 4 digits | `orders_delivery_pin_chk` |
| At most one successful payment per order | partial unique `payments_one_success_per_order_idx` |
| A webhook event is stored at most once | unique `(provider, dedupeKey)` |
| One order per idempotency key per customer | unique `(customerId, idempotencyKey)` |
| Assigned delivery has a rider; DELIVERED needs pickup plus PIN or audited override | `deliveries_rider_required_chk`, `deliveries_delivered_proof_chk` |
| A rider holds at most one active delivery | partial unique `deliveries_one_active_per_rider_idx` |
| A delivery has at most one accepted offer | partial unique `delivery_offers_one_accepted_idx` |
| Cash: reconciled ≤ collected ≤ due | `cash_collections_amounts_chk` |
| Every journal balances (checked at commit) | deferred constraint trigger `ledger_entries_balanced` |
| Each business event posts to the ledger once | unique `financial_transactions.idempotencyKey` |
| Ledger, audit log and order history are never edited or deleted | `chopnow_reject_mutation()` triggers |
| Vendor/rider payable lines name their owner | `ledger_entries_subledger_chk` |
| One live delivery-fee earning per delivery | partial unique `rider_earnings_one_fee_per_delivery_idx` |
| Payout targets exactly one beneficiary type | `payouts_beneficiary_chk` |
| An approved (or later) refund records whose money it is | `refunds_charge_to_required_chk`, `refunds_charge_to_chk`, `refunds_method_chk` |
| A successful payout records its bank reference | `payouts_bank_reference_chk` |
| One live (not failed) payout per settlement | partial unique `payouts_one_live_vendor_settlement_idx`, `payouts_one_live_rider_settlement_idx` |

Food search uses `pg_trgm` GIN indexes on `lower(name)` for menu items and restaurants.

### Rules enforced by the API (not expressible as simple constraints)
Order state transitions (`ORDER_TRANSITIONS`), ownership checks, opening hours and delivery radius, item availability at order time, COD eligibility and rider cash limits, and offer expiry.

## 4. Transaction boundaries

These operations must run in one database transaction (Prisma `$transaction`):
- **Registration:** user + profile/rider row + audit entry.
- **Order creation:** order + items + extras + status history + promotion redemption + cash collection (COD) + idempotency record.
- **Each status change:** order update + status history row (+ delivery update) + audit/notification rows.
- **Payment confirmation:** payment update + payment event + order `paymentStatus`/visibility + ledger posting.
- **Delivery completion:** delivery + order status + cash collection + rider earning + ledger postings.
- **Settlement approval and payout recording:** settlement + payout + ledger posting + audit.
- **Refund approval / completion:** refund state + ledger posting + order `paymentStatus` + audit (the provider call happens between them, outside any transaction).
- **Cash hand-in confirmation:** remittance + allocations + cash collections (rows locked) + ledger posting + audit.

External calls (Paystack and push) are never made inside a database transaction. The API records intent first, calls the provider, then records the outcome idempotently.

## 5. Data retention

| Data | Retention | Notes |
|---|---|---|
| Orders, items, status history, payments, refunds, ledger, settlements, payouts | 7 years | Financial records; never hard-deleted. |
| Audit logs | 7 years | Append-only. |
| Payment events (raw webhook payloads) | 2 years, then payload redacted | Payloads contain no card data (Paystack does not send PANs). |
| Verification documents | Life of the account + 1 year | Private bucket; deleted from storage on expiry, metadata kept. |
| Addresses | Soft-deleted on user request; order snapshots kept for the financial period | |
| Rider last position | Overwritten in place; no history kept | |
| Auth sessions | Purge 30 days after expiry/revocation | |
| Idempotency keys | Purge after `expiresAt` (24 h) | |
| Notifications | 12 months | |
| Background jobs | Purge succeeded jobs after 30 days | |

Account deletion requests deactivate the user (`status = DEACTIVATED`) and anonymise profile fields, but keep financial records. Purge jobs are scheduled in Phase 12.

## 6. Access control

- No client talks to the database. Only `services/api` holds `DATABASE_URL`. Supabase-style row-level security is not used because there is no client-side database access.
- In staging and production the API connects as `chopnow_app`, which has DML only and no TRUNCATE. On `audit_logs`, `order_status_history`, `financial_transactions` and `ledger_entries` it may only INSERT and SELECT, on top of the mutation-blocking triggers. Migrations run as `chopnow_migrator`, which owns the schema. Set up by `database/roles.sql` (which also enables `pg_trgm`); migration `20261016150000_app_role_append_only` keeps the restriction in place, and is a no-op where the role doesn't exist. See DEPLOYMENT.md §2.
- Every query for user-owned data filters by the caller's ownership in the service layer, which protects against IDOR. See `SECURITY.md`.

## 7. Commands

```bash
npm run db:migrate          # create/apply migrations in development (prisma migrate dev)
npm run db:seed             # wipe + reseed the development database with TEST data
npm run db:migrate:deploy -w @chopnow/api   # apply committed migrations (CI, staging, production)
```

To change the schema, edit `schema.prisma` and run `npm run db:migrate -- --name <change>`. Review the generated SQL. Put any check constraints or partial indexes in a hand-written migration, in ASCII.

## 8. Phase 12 changes
- `payments.lastReconciledAt` (migration `20261016160000_payment_reconciliation`): when the reconciliation sweep last asked the provider about an unconfirmed attempt. Used for the check backoff and as the per-round claim.
- Business rule `orders.unpaidOnlineOrderTimeoutSeconds` (default 1800): unpaid online orders are cancelled after this long. Stored rules without the key get the default.
